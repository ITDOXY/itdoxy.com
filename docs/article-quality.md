# Качество и публичность материалов ITDOXY

Документ согласован 6 ноября 2026 года. Основной документ для критериев приёмки и проверки публичности. Процесс и разрешения — в [editorial-workflow.md](editorial-workflow.md); выполнение проверок — в [editorial-testing.md](editorial-testing.md).

## Область проверки

Ревью относится к конкретной версии статьи, ресурсов, research или изменения системы. Указать исходную версию, согласованный объём, охват и обязательные проверки. Не объявлять весь архив исправленным после проверки выборки.

Новый стандарт применяется к новым и согласованно изменённым фрагментам. Старые дефекты вне объёма перечислить отдельно; если они делают новую рекомендацию существенно неверной или опасной, соответствующую готовность заблокировать и согласовать расширение/сужение задачи.

## Уровни замечаний

| Уровень | Примеры | Решение |
|---|---|---|
| Блокирующее | Существенно неверный/неподтверждённый тезис, выдуманный тест, утечка, опасная рекомендация без условий, ошибка обязательной сборки, потеря URL/атрибуции | Исправить либо согласовать изменение объёма; готовность заблокирована |
| Значимое | Недостаточно ясный второстепенный фрагмент, неполная навигация или объяснение | Исправить либо получить явное решение редактора с описанием последствия |
| Рекомендация | Необязательный пример, иллюстрация, небольшое стилевое улучшение | Не блокирует; записать при необходимости |

Не снижать уровень только ради завершения задачи. Предел циклов ревью задан в процессе; после него нерешённые вопросы передаются редактору.

## Критические проверки

До выполнения определить, какие проверки подтверждают существенные рекомендации и обязательные сценарии. Статусы: пройдено, не пройдено, не выполнено, не применимо. Последний статус требует обоснования применимостью, а не отсутствием времени или инструмента.

**Невыполненная критическая проверка блокирует соответствующую готовность.** Честная отметка «не выполнено» не является положительным результатом. Если среды нет, можно продолжать независимую подготовку, но нельзя принять непроверенный обязательный сценарий или статью с такой рекомендацией.

Изменение обязательных проверок и критериев требует повторного согласования по процессу. Проставление доказанных отметок выполнения задач не меняет критерии и не требует нового утверждения.

## Чек-лист статьи

| Область | Условие |
|---|---|
| Задача читателя | Соответствует brief, нет несогласованного расширения |
| Факты | Существенные тезисы подтверждены с версиями и контекстом |
| Источники | Прочитаны, точные места записаны, противоречия разрешены или отражены |
| Примеры | Указаны среда и предпосылки; тесты не выдуманы; критические выполнены |
| Безопасность | Описаны существенные последствия команд, нет реальных секретов |
| Язык | Соблюдён согласованный стиль, нет дублей и фиктивного опыта |
| Атрибуция | Авторство, перевод и оригинальные источники сохранены |
| Метаданные | Поля и формат соответствуют задаче; draft/даты не меняются автоматически |
| URL | Адрес и внутренние ссылки проверены; опубликованный slug сохранён |
| Ресурсы | Изображения доступны, relative-пути корректны, права и содержимое проверены |
| Сборка | Обязательная production-сборка по [действующему профилю](editorial-testing.md#действующий-профиль-генератора) прошла; для пилота это Hugo Extended 0.168.0 |
| Предпросмотр | Затронутые страницы визуально проверены по применимости |

Сборка подтверждает техническую сборку, но не факты, безопасность команд или права использования.

## SEO и HTML

Проверять соответствие title и description содержанию и задаче, отсутствие дубликатов/набивки ключами, логичные заголовки, категории и теги, внутренние ссылки, alt. Canonical должен соответствовать утверждённому URL. Проверять Open Graph, структурированные данные и sitemap для публикуемой страницы.

Проверять собранный HTML по [действующему профилю темы](editorial-testing.md#действующий-профиль-темы). У текущего PaperMod meta description может быть fallback, `lastmod` участвует в dateModified и Open Graph, отдельная видимая дата обновления не выводится. Эти особенности не универсальны. При смене темы заново проверить семантику страницы, метаданные и доступность; соответствие классам CSS старой темы не является критерием качества.

## Публичность: файлы и история

Публично всё отправленное в открытый Git, включая черновики, research и OpenSpec archive. `.gitignore` не очищает историю. Не считать отсутствие служебного каталога на сайте защитой его Git-содержимого.

| Проверять | Не должно попасть без соответствующего основания |
|---|---|
| Текст и конфигурация | Ключи, пароли, токены, приватные ключи, секретные параметры URL |
| Брифы, research, отчёты, OpenSpec | Закрытые планы, переписка, персональные данные и исходная аналитика |
| Изображения и вложения | Данные на скриншотах, лишние метаданные, приватные исходники |
| Логи и fixtures | Реальные credentials, чувствительные ответы систем, несогласованные локальные пути |
| Чужие материалы | Полные тексты, транскрипции, код и изображения без проверки условий |
| Git | Секреты в промежуточных коммитах, даже удалённые из итогового дерева |

Ручная проверка охватывает смысл и конфиденциальность. Автоматический поиск — вспомогательный; имя конкретного сканера, версия и команда записываются, когда он действительно выбран и запущен. GitHub secret scanning не заменяет проверку до push. [Описание secret scanning](https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning)

Обязательный охват перед решением о коммите: working tree, новые, staged и двоичные файлы предполагаемого изменения. До публичного push: итоговые файлы и все новые отправляемые коммиты относительно зафиксированной целевой базы. Перед PR и после изменений — актуальный head и новые данные. Проверять только итоговый diff недостаточно.

Отчёт публичности должен содержать цель проверки, base/head или checksums незакоммиченных файлов, список/диапазон, типы файлов, команды/ручные действия, замечания, ограничения и решение. Секрет целиком не выводить: путь и безопасная классификация достаточны. При неполном охвате статус — «не оценено/не готово», а не «пройдено».

Если секрет уже отправлен, остановить дальнейшую отправку и сообщить владельцу о необходимости отдельного устранения последствий. Автоматически переписывать историю или считать удаление файла достаточным нельзя.

## Результат article-review

Будущий review.md содержит: проверенную версию и границы; фактические проверки; замечания с уровнем и доказательством; исправления; невыполненные пункты; решения по значимым вопросам; ограничения; отдельные verdict для текста/системы, публичной отправки и выпуска.

Вердикты: готово к редакторскому просмотру, требуются изменения, заблокировано, не оценено. Они не разрешают commit, push или deploy. Утверждение пользователя записывается отдельно и действительно только для проверенной версии.

Пилот принимается, когда обязательные сценарии проверены и блокирующих проблем нет. При невозможности доказать критический результат — «не принято», либо предложение delta требований на согласование. Завершённая валидация OpenSpec не подменяет эти условия.
