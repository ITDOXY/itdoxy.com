# Внедрение AI-редакции ITDOXY через Codex Desktop и OpenSpec

Согласованный план внедрения от 5 ноября 2026 года. Источник — окончательная инструкция из чата после ревью 12 замечаний и двух финальных уточнений. Текущее выполнение фиксируется в [ai-editorial-progress.md](ai-editorial-progress.md).

Это план внедрения, а не утверждение о готовности описанных возможностей. Публичное руководство по использованию создаётся отдельно в `docs/ai-editorial.md`.

Цель — организовать воспроизводимую подготовку, проверку и актуализацию технических статей на русском языке.

Codex Desktop выполняет исследование, согласованные изменения и проверки. OpenSpec описывает требования к редакционной системе и управляет её развитием. Пользователь утверждает объём работы, принимает решение о коммите и разрешает публичную отправку и выпуск.

Порядок внедрения:

```text
Проверка проекта
  → редакционные документы и публичное руководство
  → AGENTS.md и критерии приёмки
  → OpenSpec
  → спецификация article-update
  → три Skills пилота
  → проверка загрузки Skills
  → изолированный пилот
  → приёмка
  → остальные режимы
  → качество и публичность
  → решение пользователя о коммите
  → проверка отправляемой истории
  → push и PR
  → проверка окончательной версии
  → решение пользователя о выпуске
```

**Сначала создаются редакционные документы, затем обновляется `AGENTS.md`.**

## 1. Зафиксировать состав MVP и полномочия

Пользовательские режимы:

| Skill | Назначение |
|---|---|
| `article-from-sources` | Статья по теме и предоставленным источникам |
| `article-from-topic` | Исследование темы и подготовка статьи |
| `discover-topics` | Предложения тем на основе архива |
| `article-update` | Проверка и обновление существующей статьи |
| `content-audit` | Реестр архива и очередь обновлений |

Общие Skills:

| Skill | Назначение |
|---|---|
| `research` | Источники, доказательства, версии, противоречия и ограничения |
| `article-review` | Факты, примеры, язык, SEO, Hugo и публичность |

Сначала реализуются `research`, `article-review` и `article-update`. Остальные режимы — после приёмки пилота.

Обязательные границы:

- Codex изменяет только согласованные файлы и выполняет разрешённые проверки.
- **Коммит делает пользователь самостоятельно либо Codex по явному запросу.**
- Утверждение плана, выполнение OpenSpec tasks и успешные проверки не разрешают commit или amend.
- Скрипты, хуки и задачи OpenSpec не должны автоматически создавать коммиты.
- Разрешение на commit не разрешает push.
- Push, создание PR, merge, снятие `draft` и запуск deploy выполняются только в явно разрешённом объёме.
- Разрешение на одно действие не становится постоянным разрешением.

OpenSpec используется при разработке и изменении редакционной системы. Для обычной статьи достаточно задания, research, плана, ревью и процесса публикации.

## 3. Подготовить ветку и базовую сборку

Промпт:

```text
Подготовь ветку chore/ai-editorial-pilot.

Сначала проверь рабочее дерево.
При незакоммиченных изменениях покажи список.
Не выполняй stash, сброс или переключение веток.

При чистом дереве:
- обнови main через fast-forward при доступной сети;
- создай ветку;
- проверь submodules на закреплённых версиях.

Не обновляй тему.
Не выполняй commit, push или публикацию.

Проверь базовую сборку.
Раздели результаты на локальном Hugo
и Hugo Extended 0.168.0 из CI.
Не меняй CI ради совпадения с локальной установкой.
```

Команды при чистом рабочем дереве:

```bash
git status --short
git switch main
git pull --ff-only
git switch -c chore/ai-editorial-pilot
git submodule update --init --recursive
hugo version
hugo --minify
```

Для приёмки подготовьте отдельный бинарник Hugo Extended `0.168.0` либо подходящую изолированную среду. Запишите точную команду запуска в документации.

Локальная сборка на другой версии не заменяет проверку совместимости с CI.

**Контрольная точка:** есть рабочая ветка и исходные результаты сборки с указанием версии.

## 5. Определить критерии качества и приёмки до пилота

### Работа с источниками

- Читать источники, а не только поисковые сниппеты.
- Проверять технические утверждения по первичным источникам.
- Учитывать версии, даты и контекст.
- Не считать пересказы независимыми подтверждениями.
- Фиксировать противоречия.
- Не выдумывать личный опыт, просмотр видео и тестирование.
- Сохранять авторство и атрибуцию.
- Различать устаревание и историческую применимость.

Замечания делятся на блокирующие, значимые и рекомендации. Существенная ошибка, утечка данных, выдуманное тестирование или ошибка обязательной сборки блокируют соответствующую готовность.

Установите предел исправлений, например два цикла. Нерешённые вопросы передаются редактору.

### Выполнение примеров

На основном компьютере разрешены только согласованные проверки проекта.

Команды из статей не выполняются автоматически. Установка пакетов, изменение ОС, запуск инфраструктуры, операции с дисками и данными требуют определения среды и границ.

Используйте подходящую одноразовую VM или контейнер, когда он действительно обеспечивает нужную изоляцию. Не подключайте реальные ключи, production-контексты и рабочие данные.

Временная копия сайта изолирует файлы, но сама по себе не изолирует выполнение команд.

При отсутствии среды записывайте:

```text
Статус: не выполнено.
Причина: <причина>.
Ограничение достоверности: <последствие>.
```

**Статус «не выполнено» не означает приёмку.**

Если проверка необходима для подтверждения существенной рекомендации статьи или обязательного сценария пилота, соответствующая готовность остаётся заблокированной.

Критичность проверок определяйте до запуска. Нельзя объявлять проверку необязательной только потому, что её не удалось выполнить. Изменение критериев требует согласования.

### Публичность

Обязательные точки:

1. Перед решением о коммите — рабочие, новые и staged-файлы.
2. До публичного push — все новые отправляемые коммиты.
3. Перед PR и после изменений — актуальное состояние и новая история.

Приватные сведения блокируют публичную отправку.

## 7. Подготовить research и хранение данных

Структура:

```text
docs/editorial-templates/
research/<article-id>/
reports/editorial/
scripts/editorial/
work/editorial/
```

Досье:

| Файл | Содержание |
|---|---|
| `brief.md` | Задание, границы, путь, URL, исходная версия |
| `sources.yaml` | Источники, версии, доступность и точные места |
| `findings.md` | Тезисы и доказательства |
| `outline.md` | План и утверждение |
| `verification.md` | Проверки, результаты и ограничения |
| `review.md` | Замечания и решение |

`article-id` должен оставаться стабильным при изменении заголовка.

Добавьте `/work/editorial/` в `.gitignore`. Проверьте уже отслеживаемые файлы: правило не удаляет их и не очищает историю.

Конфиденциальные материалы храните вне репозитория. В публичный Git переносите только подготовленное досье.

Не публикуйте ключи, переписку, закрытые брифы, персональные данные, исходную аналитику и полные чужие материалы без соответствующего разрешения.

`draft: true` не скрывает файл на GitHub.

Пример реестра:

```yaml
schema_version: 1
article_id: "<article-id>"
provenance: "new"
sources:
  - id: "S01"
    url: "<точный URL>"
    title: "<название>"
    type: "official-docs"
    accessed_at: "<YYYY-MM-DD>"
    software_version: "<версия или null>"
    access_status: "read"
    locator: "<раздел или таймкод>"
```

Archetype содержит только `title`, `date`, `draft`. Остальные поля добавляет редакционный процесс. YAML и TOML поддерживаются без массовой конвертации. Автора нельзя придумывать.

## 8. Настроить воспроизводимый OpenSpec

Выберите точную версию по официальным релизам и сохраните:

- номер версии;
- способ установки;
- точную команду повторной установки;
- профиль;
- список сгенерированных Skills.

Для npm требуется Node.js `22.12.0+`. После выбора версии:

```text
npm install -g @fission-ai/openspec@<точная-версия>
```

Заполнитель нужно заменить реальным номером.

Homebrew допустим для первой установки:

```bash
brew install openspec
openspec --version
```

Для воспроизводимости отдельно зафиксируйте способ получения выбранной версии.

Инициализация:

```bash
openspec init --tools codex --profile core
```

Явный профиль исключает зависимость набора workflow от глобальной настройки. [Справка OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/main/docs/cli.md)

Промпт:

```text
Инициализируй выбранную версию OpenSpec с профилем core.
Покажи созданные и изменённые файлы.

Сохрани действующие инструкции.
Не создавай все спецификации сразу.
Не настраивай автоматические коммиты.
Не выполняй commit, push или публикацию.
```

В конфигурации сохраните контекст ITDOXY и ссылки на документы. Не копируйте туда все редакционные нормы.

## 9. Создать спецификацию пилота `article-update`

Промпт:

```text
Используй сгенерированный Skill openspec-propose.
Создай change add-article-update-pilot.

Включи article-update и минимально необходимые
research и article-review.

Сначала proposal, specs, design и tasks.
Реализацию не начинай.

Используй согласованные критерии качества,
публичности и безопасного тестирования.

Не включай остальные режимы, тему, CI и публикацию.
В tasks не должно быть автоматических commit/amend.
```

Структура:

```text
openspec/changes/add-article-update-pilot/
├── proposal.md
├── design.md
├── tasks.md
└── specs/
    ├── article-update/spec.md
    ├── research/spec.md
    └── article-review/spec.md
```

Сценарии:

| Условие | Ожидаемый результат |
|---|---|
| Нет research | Досье восстановлено с отметкой происхождения |
| Нет утверждения объёма | Статья не меняется |
| Малый update | Нет полной переработки |
| Источник недоступен | Ограничение записано |
| Источники противоречат | Противоречие сохранено |
| Нет безопасной среды | Пример не исполняется |
| Критическая проверка не выполнена | Соответствующая готовность заблокирована |
| Есть приватные данные | Публичная отправка заблокирована |
| Изменения не нужны | Нет искусственных правок |
| Повторный запуск без новых данных | Нет дублей и ненужных изменений |
| Работа прервана | Возобновление из проверенного состояния |
| Исходник изменился | Старый план не применяется автоматически |
| Требования изменились | Новое согласование |
| Задача завершена | Нет автоматического коммита |
| Пилот выполнен | Оригинал и ресурсы неизменны |

### Фиксация согласования

Сохраните:

- идентификатор change;
- исходную версию статьи;
- версии proposal, specs и состава tasks;
- согласованные границы;
- обязательные проверки;
- дату и сообщение утверждения.

Для незакоммиченных файлов используйте контрольные суммы. Коммит ради согласования не требуется.

Повторное утверждение необходимо при изменении:

- требований;
- объёма;
- критериев приёмки;
- обязательных проверок;
- состава или смысла задач.

Порядок:

```text
Показать delta
  → объяснить последствия
  → остановить зависимую реализацию
  → получить утверждение
  → зафиксировать новую версию
```

**Проставление подтверждённых отметок выполнения в `tasks.md` не требует нового утверждения**, если требования и смысл задач не изменились.

То же правило применяется к согласованному объёму обновления статьи.

## 10. Реализовать Skills и проверить загрузку

Структура каждого Skill:

```text
.agents/skills/<name>/SKILL.md
```

Обязательные метаданные:

```markdown
---
name: article-update
description: >-
  Проверяет и обновляет конкретную статью ITDOXY.
  Для аудита архива используй content-audit.
---
```

Файл содержит вход, шаги, допустимые изменения, ссылки, контрольные точки, результаты и критерии завершения. [Документация Skills](https://learn.chatgpt.com/docs/build-skills)

Промпт:

```text
Реализуй утверждённую версию add-article-update-pilot
через openspec-apply-change.

Создай research, article-review и article-update.
Отмечай задачи только после проверки.

При изменении согласованного поведения
покажи delta и останови зависимую работу до утверждения.

Не меняй тему, Hugo или CI.
Не создавай коммиты.
```

В новом последовательном Local-чате:

```text
Проверь путь и ветку.

Покажи, обнаружены ли репозиторные Skills:
article-update, research, article-review.

Прочитай ожидаемые SKILL.md и укажи точные пути.
Проверь метаданные.

Покажи, как article-update применяет общие Skills.
Статьи пока не изменяй.
```

Проверяется:

- Skill обнаружен;
- прочитан ожидаемый файл;
- нет подмены одноимённым личным Skill;
- общие инструкции действительно применяются.

Ответа «использую article-update» недостаточно.

При необнаружении обновите контекст или перезапустите приложение. До исправления пилот не запускается.

## 11. Подготовить изолированную копию сайта и выполнить пилот

Не создавайте вторую статью с тем же slug внутри рабочего `content/posts/`: она конфликтует с исходным URL даже при preview с `-D`.

Создайте отдельную временную копию всего сайта вне рабочего репозитория:

- сохраните исходный путь статьи;
- включите bundle и ресурсы;
- включите закреплённые файлы темы;
- исключите `.git`, старые сборки и конфиденциальные файлы;
- убедитесь, что изменяемые файлы не ссылаются на оригинал.

Запишите путь копии и контрольные суммы оригинальной статьи и ресурсов.

Промпт:

```text
Подготовь отдельную тестовую копию всего сайта
вне рабочего репозитория.

Не добавляй дубликат статьи в рабочий content/.
Сохрани исходный путь, slug и ресурсы в тестовой копии.
Материализуй нужные файлы темы.

Зафиксируй пути и контрольные суммы оригинала.
Ничего не коммить.
```

Затем:

```text
Примени article-update только к тестовой копии.

Сначала research и предложение изменений.
Дождись утверждения объёма.

Примеры не выполняй на основном компьютере.
При отсутствии согласованной среды отметь их непроверенными.
Критические непроверенные пункты блокируют готовность.
```

Восстановленное досье различает:

- источники из статьи;
- источники, найденные сейчас;
- исторически верные тезисы;
- устаревшие тезисы;
- неподтверждённые тезисы.

Используйте `provenance: reconstructed` и дату восстановления. Сохраняйте атрибуцию оригинала.

После утверждения внесите согласованные изменения, проведите ревью и проверки.

Для сценариев сохраняйте:

```text
scenario → input → expected → actual → evidence → status
```

Сверьте контрольные суммы оригинала. Тестовые статьи и сборки не включаются в предлагаемые изменения.

## 12. Принять пилот и архивировать change

До приёмки должны пройти:

- загрузка трёх Skills;
- обязательные сценарии;
- безопасные проверки;
- проверка публичности предлагаемых файлов;
- неизменность оригинала;
- сборка на Hugo Extended `0.168.0`;
- отсутствие автоматических commit/amend в скриптах, хуках и tasks.

Проверки OpenSpec:

```bash
openspec validate add-article-update-pilot --strict
openspec validate --all --strict
```

Валидация структуры не доказывает выполнение сценариев.

Возможные решения:

| Решение | Условие |
|---|---|
| Принято | Обязательные проверки выполнены, блокирующих проблем нет |
| Не принято | Есть дефект или невыполненная критическая проверка |
| Требуется изменение требований | Подготовлена delta для повторного согласования |

Не принимайте пилот с невыполненным обязательным сценарием. Не меняйте критерии задним числом без утверждения.

После явной приёмки:

```bash
openspec archive add-article-update-pilot --yes
openspec validate --all --strict
```

Archive обновляет файлы OpenSpec, но не разрешает Git-коммит или выпуск.

Обновите ссылки и статус в `docs/ai-editorial.md`.

## 13. Реализовать остальные режимы

Последовательно:

| Change | Режимы |
|---|---|
| `add-article-creation-modes` | `article-from-sources`, `article-from-topic` |
| `add-editorial-discovery-audit` | `discover-topics`, `content-audit` |

Для каждого:

```text
Предложение → утверждение версии → реализация
           → проверка загрузки Skills
           → сценарии → приёмка → архивирование
```

Не дублируйте общие Skills. Их изменения описывайте явно и повторяйте затронутые проверки пилота.

Обязательное поведение:

- Для создания статьи исследование предшествует тексту.
- План утверждается до написания.
- Новая статья имеет `draft: true`.
- Обновление сохраняет исходный `draft`.
- Аналитические режимы не создают статьи.
- Поиск тем не выдумывает метрики спроса.
- Аудит указывает охват и различает риск и доказанный дефект.
- Повторные запуски не создают искусственных правок.
- Изменения критериев повторно согласуются.

Продолжение **только для режимов создания**:

```text
Утверждаю план новой статьи.
Подготовь черновик и выполни article-review.
Сохрани draft: true.
Проверь публичность.
Коммит и публикацию не выполняй.
```

Для обновления:

```text
Утверждаю объём для зафиксированной версии статьи.
Внеси правки, сохрани исходный draft,
обнови research и выполни проверки.
Коммит и публикацию не выполняй.
```

## 14. Добавить видео, SEO и повторяемые проверки

Видео исследуется по доступному содержимому, субтитрам или предоставленному файлу. Фиксируются автор, URL, дата, происхождение текста и таймкоды.

Название не подтверждает просмотр. Субтитры не подтверждают экран. Отсутствие данных записывается как ограничение.

Обработчик SRT/VTT добавляйте отдельным change после основного пилота. Он должен:

- сохранять таймкоды и UTF-8;
- поддерживать многострочные реплики;
- не перезаписывать вход;
- не удалять смысловые повторения;
- не скачивать видео и не вызывать платные сервисы без разрешения.

SEO-проверка включает:

- title и description;
- slug и конфликты URL;
- заголовки и внутренние ссылки;
- категории и теги;
- изображения, alt и права использования;
- canonical, Open Graph, Schema.org и sitemap.

Особенности ITDOXY:

- description может использовать запасной текст;
- `lastmod` применяется в метаданных;
- отдельная видимая дата обновления сейчас не выводится;
- шаблоны проверяются по актуальным путям.

Автоматизация проверяет front matter через штатный парсер или Hugo, поля, файлы, связи research и конфликты URL. Она не заменяет проверку фактов и конфиденциальности.

Команды:

```bash
hugo --minify
hugo server -D --bind 127.0.0.1
openspec validate --all --strict
```

Для приёмки используйте Hugo `0.168.0`. Production и preview собирайте в свежие отдельные каталоги.

## 15. Проверить публичность и отправляемую историю

### Перед решением о коммите

Проверьте рабочие, новые и staged-файлы:

- документы и OpenSpec changes;
- research и отчёты;
- скрипты и fixtures;
- изображения и метаданные;
- логи и результаты инструментов.

Ищите секреты, персональные данные, закрытые планы, приватные URL, лишние локальные пути, аналитику и неразрешённые исходники.

Не выводите секреты целиком. Записывайте путь, тип проблемы и необходимое действие.

Codex выдаёт diff, проверки, ограничения и предлагаемый текст коммита. Пользователь делает коммит самостоятельно либо явно поручает его Codex.

### До публичного push

Итогового diff недостаточно. Проверьте все новые отправляемые коммиты, включая промежуточное содержимое файлов.

Зафиксируйте:

- целевую базу и SHA;
- head ветки;
- диапазон проверенных коммитов;
- отправляемую ветку;
- охват проверок.

Секрет, добавленный одним коммитом и удалённый следующим, всё равно отправляется вместе с историей.

Не используйте push всех веток или тегов. Разрешение относится к конкретному проверенному набору.

Промпт:

```text
Проверь публичность перед отправкой ветки.

Зафиксируй базу, head и новые отправляемые коммиты.
Проверь итоговые файлы и промежуточное содержимое истории.

Покажи охват, проблемы и ограничения.
Секреты целиком не выводи.
Push не выполняй.
```

Если проблема уже в локальной истории, предложите исправление. Не выполняйте amend, rebase или другое переписывание без отдельного запроса.

Перед PR и после новых изменений повторите затронутые проверки и зафиксируйте актуальный head.

## 16. Подготовить PR, выпуск и откат

Рекомендуемые PR:

1. Документы, публичное руководство, OpenSpec и пилот.
2. Остальные режимы.
3. Реальные публикационные материалы.

Перед каждым проверяются качество, публичность файлов и история.

Текущий workflow не проверяет PR. Добавление такого CI — отдельное изменение без секретов деплоя.

### Окончательная версия выпуска

Workflow публикует после push в `main` и `workflow_dispatch`. Ручной запуск нельзя использовать как проверку сборки.

Перед merge:

1. Зафиксировать окончательный head PR и актуальный SHA базы.
2. Проверить совмещённое состояние, которое попадёт в `main`.
3. Собрать его на Hugo `0.168.0`.
4. Сравнить наличие и адреса опубликованных страниц.
5. Подтвердить редакционное согласование этой версии.
6. Проверить публичность новых изменений и истории.

Совмещённое состояние можно проверять в отдельном временном checkout без создания коммита. В отчёте фиксируются база, head и проверенное дерево.

После правок, обновления базы или разрешения конфликтов прежнее утверждение не переносится автоматически. Повторяются затронутые проверки и согласование.

Снятие `draft` новой статьи требует отдельного разрешения. При обновлении исходный статус сохраняется.

После выпуска проверьте SHA успешного workflow, результат деплоя и целевые URL.

### Откат

Деплой использует `--delete`: отсутствующие в сборке файлы удаляются из бакета.

Откат готовится в отдельной ветке без коммита:

```bash
git revert --no-commit <commit_sha>
```

Для merge commit после проверки родителей:

```bash
git revert --no-commit -m 1 <merge_commit_sha>
```

Затем — сборка, проверка URL, согласованности specs и Skills, публичности, diff и решение пользователя о коммите.

Никаких автоматических commit, push, merge или deploy.

### Критерии готовности

MVP принимается, когда:

- публичное руководство соответствует реализации;
- документы созданы до обновления `AGENTS.md`;
- OpenSpec воспроизводимо настроен;
- пилот `article-update` принят до остальных режимов;
- загрузка Skills проверена;
- тестовый сайт изолирован, оригинал неизменен;
- примеры выполняются только в согласованных средах;
- невыполненные критические проверки блокируют готовность;
- изменение требований повторно утверждается;
- подтверждённые отметки выполнения не требуют лишнего согласования;
- research содержит доказательства и ограничения;
- публичность проверяется до push, перед PR и после изменений;
- отправляемая история проверена;
- коммиты остаются решением пользователя;
- выпуск связан с проверенными SHA и состоянием сайта;
- откат учитывает URL, спецификации и `--delete`.

Начинать можно с документов и спецификации. Поведенческий пилот запускается после подготовки изоляции, проверки загрузки Skills, согласования безопасных сред и критериев приёмки.

После приёмки используйте отдельный последовательный чат для статьи или аудита и сохраняйте решения в файлах.
