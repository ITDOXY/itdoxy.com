# Редакционный стиль ITDOXY

Документ согласован 6 ноября 2026 года. Основной документ для языка, структуры и оформления. Основание: [выборка 12 статей](editorial-repository-audit.md). Требования относятся к новому и согласованно изменяемому контенту; весь архив автоматически не переписывается.

## Аудитория и тон

ITDOXY объясняет практические задачи администрирования, разработки, баз данных и AI-инструментов. Уровень читателя и ожидаемый результат задаются в brief; статья не должна одновременно предполагать новичка и требовать неоговорённой экспертизы.

Предлагаемый тон: спокойный, конкретный, доброжелательный. Обращение — «вы» со строчной буквы; допустим нейтральный безличный текст. Существующий авторский голос сохраняется, если не мешает точности. Не превращать разговорность отдельных статей в обязательное правило.

Убирать рекламные превосходные степени, неподтверждённые обещания, шаблонные вступления и повторяющиеся выводы. Вместо «полностью безопасно» описывать границы и условия. Числа, сроки, проценты и сравнения должны иметь контекст и доказательства по [research-policy.md](research-policy.md).

Не создавать впечатление личного опыта, которого нет. «Мы проверили» допустимо только при наличии соответствующего результата в verification. Отчёт о проверке документации не равен запуску программы. Мнение, иллюстративный пример и факт обозначаются раздельно.

## Язык и терминология

- Писать по-русски, последовательно использовать «ё» в обычном тексте; не менять имена, URL и код ради этого правила.
- При первом существенном упоминании объяснять термин или сокращение в контексте задачи. Сохранять точные имена продуктов, API, параметров и версий.
- Использовать короткие связные абзацы. Списки — для шагов или параллельных пунктов, таблицы — для сравнения по одинаковым основаниям.
- Не злоупотреблять жирным выделением, эмодзи, восклицаниями и англицизмами. Не копировать речевые ошибки старых переводов.

## Структура

Заголовок обещает результат, который статья действительно даёт. В начале: задача, применимость, существенные ограничения. Для инструкции: предпосылки, версии/платформа, шаги с целью, ожидаемый результат и проверка, ограничения и безопасное завершение.

Для обзора или сравнения: критерии выбора, сопоставимые условия, аргументы, ограничения. Не требовать от короткого справочного материала искусственных разделов.

Шаблон сайта уже выводит H1 из title. В теле начинать с H2 и сохранять логичную вложенность. Заголовки описывают содержание; нумерация нужна для последовательных действий. Не дублировать абзацы и не дополнять объём ради объёма.

## Переносимость содержания

По умолчанию писать переносимый Markdown: заголовки, списки, таблицы, блоки кода, обычные ссылки и изображения. Не вводить новый shortcode, компонент или необязательный raw HTML без необходимости. Если формат зависит от генератора, фиксировать это и сохранять понятный исходный материал. Существующие конструкции не переделывать вне согласованного объёма.

Смысл метаданных — заголовок, описание, авторство, даты, адрес и состояние публикации — сохраняется при переносе; имена полей и способ чтения определяет профиль генератора. Ниже — правила действующего Hugo, а не общая схема для будущих платформ.

Не завязывать смысл статьи на класс CSS, цвет или расположение блока в PaperMod. Значимые предупреждения, порядок шагов и подписи должны быть понятны в самом тексте. Особенности оформления и отображения полей сверять по [профилю темы](editorial-testing.md#действующий-профиль-темы).

## Метаданные и пути

- Сохранять принятые имена `YYYY-MM-DD-title.md` или `YYYY-MM-DD-title/index.md`. Не переименовывать существующий файл автоматически.
- Для новой статьи заполнить title, slug, ISO 8601 date с часовым поясом, categories, подтверждённые авторские метаданные и явный draft. Для новой страницы заполнить содержательный description, который действительно поддерживается темой.
- Archetype не заполняет полный набор. Не назначать автором Codex или владельца сайта без редакционного решения. Если автор неизвестен, зафиксировать вопрос; не публиковать фиктивное имя.
- Для старого материала без явного author сохранить существующие данные и описать наследование автора сайта; не превращать отсутствие поля в разрешение переписать авторство.
- Использовать существующие категории и теги. Новую таксономию предложить с обоснованием.
- YAML — два пробела. Существующий TOML сохранять; массовая конвертация не нужна.
- Опубликованные slug, URL, исходная date, авторство и атрибуция сохраняются. Осознанное изменение URL — отдельное решение с проверкой переходов.
- lastmod добавлять/менять при содержательном обновлении с фактической датой; не изображать свежесть ради SEO. Исправление опечатки не требует автоматического обновления lastmod.

Не считать весь старый архив неготовым только из-за отсутствия новых полей. Изменения старых метаданных входят в согласованный объём. Правила draft и выпуска — в [процессе](editorial-workflow.md).

## Код и команды

Каждый fence имеет подходящий язык: `bash`, `python`, `sql`, `java`, `yaml`, `toml`, `html`, `text` и т. п. Вывод отделяется от вводимой команды. Не смешивать shell prompt и копируемую команду без пояснения.

Показывать минимальный пример, нужный для задачи. Обозначать файлы, рабочий каталог, версии и предпосылки. Не переносить трекинговые скрипты, реальные credentials и посторонний код из чужих примеров. Для продолжений строк сохранять корректное экранирование; проверять ASCII-дефисы в параметрах.

Заполнители должны быть очевидны и описаны. Не выдавать неполный фрагмент за готовую программу. Потенциально разрушительные действия объясняются до команды: что меняется, какая среда нужна и как проверить результат. Исполнение регулирует [editorial-testing.md](editorial-testing.md).

## Изображения, ссылки и атрибуция

Обложка bundle задаётся через cover.image и cover.relative: true; файл действительно должен находиться в bundle. При обновлении сохранять связность относительных ресурсов. Не копировать только index.md без нужных файлов.

У содержательных изображений — информативный alt и при необходимости подпись. Для декоративных допустим пустой alt. Скриншот проверять на персональные данные и секреты. Внешнее изображение может исчезнуть; оно не должно быть единственным доступным описанием команды или результата. Локализация чужого изображения требует проверки условий использования.

Ссылки имеют понятные подписи. Внутренние адреса должны существовать и соответствовать текущей структуре. Не удалять источник перевода и не представлять перевод как собственное оригинальное исследование. Порядок атрибуции — в [политике исследования](research-policy.md).

## SEO без подмены содержания

Уникальность и полезность title/description проверяются по смыслу. Заполнение поля keywords не заменяет содержательную статью; не использовать набивку ключевыми словами. Оглавление, canonical, preview и структурированные данные проверять в реальном HTML по [критериям качества](article-quality.md).

В текущем PaperMod с переопределениями ITDOXY отдельная видимая дата обновления не выводится. При замене темы сверить её отображение по собранной странице; не обещать вывод без проверки.
