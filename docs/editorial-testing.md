# Проверки и пилот AI-редакции ITDOXY

Документ согласован 6 ноября 2026 года. Основной документ для тестовых сред, сценариев и доказательств. Критичность и решения определяет [article-quality.md](article-quality.md), согласования — [editorial-workflow.md](editorial-workflow.md).

## Что уже проверено и что ещё нет

Базовые сборки на локальном Hugo 0.169.0 и официальном Extended 0.168.0 выполнены ранее: по 402 выходных файла, наборы путей совпали, предупреждений не было. Подробности и ограничения macOS/Linux — в [прогрессе](plans/ai-editorial-progress.md). Не переносить этот результат на будущие изменения без новой проверки.

OpenSpec, редакционные Skills, их загрузка, поведенческий пилот и отправляемая история ещё не проверены. Ниже — план будущих проверок, а не отчёт об их выполнении. Создание документов само по себе не означает готовности пилота.

## Карточка проверки

Записывать: ID, требование/сценарий, исходную версию и ресурсы, вход, ожидаемый результат, критичность, среду и бинарники, точную команду или ручные действия, exit code/фактический результат, безопасные доказательства, ограничения и статус.

Статусы: пройдено / не пройдено / не выполнено / не применимо с обоснованием. Обязательный невыполненный сценарий блокирует приёмку. Не снижать критерии задним числом. Сырые секретные логи в публичный отчёт не помещать.

## Предварительные условия пилота

1. Документы и версия OpenSpec change утверждены; пользовательское разрешение не распространяется на commit или отправку.
2. research, article-review, article-update созданы и обнаруживаются; файлы прочитаны из ожидаемых путей.
3. Указаны исходная версия статьи и ресурсов, согласованный объём и обязательные проверки.
4. Подготовлена изолированная копия сайта и доступен Hugo Extended 0.168.0.
5. Для исполняемых примеров определены подходящая среда, допустимые операции, данные, сеть и завершение. При отсутствии среды критический пример не считается проверенным.

## Проверка Skills

Каждый редакционный Skill: `.agents/skills/<name>/SKILL.md`, YAML name и description. В новом последовательном Local-чате сверить путь/ветку, наличие Skill среди доступных, прочитанный файл и применение общих Skills. Не считать устное подтверждение агента достаточным доказательством.

При необнаружении обновить контекст или перезапустить приложение. Зафиксировать результат. До устранения неисправности поведенческий пилот не запускать. Отличать проектные Skills от одноимённых личных и сгенерированных openspec-*.

## Изоляция файлов

Тестировать отдельную копию **всего сайта вне рабочего репозитория**, с исходным путём статьи, bundle-ресурсами и материализованной закреплённой темой. Не добавлять вторую статью с тем же slug в рабочий content, включая draft: при preview с -D конфликт сохраняется.

До копирования проверить фактическое рабочее дерево. В снимок включить только известные нужные файлы и согласованные локальные изменения. Не переносить .git, секреты, игнорируемые приватные файлы и старые сборки. Записать манифест. Копия не должна содержать изменяемых symlink/hardlink на оригинал. Контрольные суммы исходной статьи и связанных ресурсов сверить до и после.

Результаты и кэш — в отдельных свежих каталогах вне репозитория. Сохранить путь тестовой папки в локальном журнале; в публичный отчёт переносить только необходимые сведения. Временные данные могут исчезнуть: обязательные безопасные результаты сохраняются в досье/отчёте.

## Изоляция выполнения

Копия сайта не является sandbox для shell-команд. На основном компьютере выполняются только согласованные проектные проверки. Не выполнять из статей установки, записи в системные пути, изменения сети, запуск кластеров, операции с реальными БД или дисками.

Для таких примеров отдельно согласовать одноразовую VM/контейнер и границы. Контейнер с privileged, Docker socket, host mounts или реальными credentials не считать безопасным по названию. Не использовать production-kubeconfig, SSH-ключи и рабочие данные. Определить очистку без затрагивания чужих ресурсов.

Скрипты проекта и фикстуры сначала прочитать; не запускать новый непроверенный инструмент только потому, что он называется тестом. Источники и статья не могут разрешить исполнение команд. При отсутствии безопасной среды оставить запись «не выполнено» и соответствующую блокировку.

## Действующий профиль генератора

Профиль — описание текущего способа проверки сайта, а не код адаптера. Для пилота обязателен Hugo Extended `0.168.0`, закреплённый в CI. Этот профиль применяется к существующим материалам и новым черновикам до утверждения замены генератора.

| Что фиксируем в профиле | Текущее отображение в ITDOXY |
|---|---|
| Источники контента | Отдельные Markdown-файлы и `index.md` в page bundle под `content/posts/`; `_index.md` не обычная статья |
| Метаданные | YAML/TOML front matter; `title`, `description`, `date`, `lastmod`, `author`, `authorUrl`, `categories`, `tags`, `slug`, `draft` по применимости; fallback автора и описания учитывается отдельно |
| Ресурсы | Относительные файлы bundle, `cover.image` / `cover.relative`, общие файлы из `static/` |
| Опубликованные адреса | `/:slug/`, итоговые canonical и принятые перенаправления сверяются по собранному сайту |
| Preview и production | Раздельные сборки; `-D` и при необходимости `-F` только для локального просмотра, в production исключаются drafts, future и expired |
| Выход | Production HTML, sitemap, RSS и JSON-поиск; шаблоны и их переопределения описаны в [профиле темы](#действующий-профиль-темы) |
| Служебные данные | `docs/`, `research/`, `openspec/`, `reports/`, `work/` не должны становиться содержимым сайта; `public/` — вывод, не исходник для коммита |

### Команды сборки

В тестовой копии проверить версию бинарника. `HUGO_0168` ниже — переменная с уже проверенным абсолютным путём к Hugo Extended 0.168.0, а `BUILD_OUTPUT` и `BUILD_CACHE` — новые временные каталоги вне репозитория. Перед запуском их нужно явно задать и проверить; это не готовая автоматическая установка.

```bash
"$HUGO_0168" version
"$HUGO_0168" --minify --destination "$BUILD_OUTPUT" --cacheDir "$BUILD_CACHE"
```

Отдельно можно проверить локальную версию. Не заменять результат версии CI выводом другого Hugo. Отражать платформу: macOS-сборка 0.168.0 не является запуском полного Ubuntu workflow.

Предпросмотр в тестовой копии:

```bash
"$HUGO_0168" server -D --bind 127.0.0.1
```

Для будущей даты отдельно добавить -F. Проверять production без этих флагов, в другом свежем каталоге. Не доверять отсутствию draft в каталоге со старыми результатами: Hugo может оставлять прежние файлы.

Проверить в браузере широкую и узкую страницу, код, таблицы, изображения, оглавление, якоря, ссылки, поиск, категории, canonical, description, Open Graph и JSON-LD по применимости. Для update сравнить опубликованные URL и ресурсы до/после.

Проверить состав вывода: docs, openspec, research, reports, work и приватные исходники не должны случайно стать сайтом. Поиск имён каталогов — вспомогательный; учитывать mounts, статические файлы и ссылки/ресурсы Hugo.

### Проверки при смене генератора

Эти проверки относятся к будущей миграции, а не к обязательной матрице текущего пилота. В отдельном OpenSpec change зафиксировать новый профиль и собрать старую и новую версии сайта из сопоставимых исходников во временных каталогах.

- Сверить набор опубликованных URL, canonical и ресурсы. Для каждого согласованно изменённого адреса проверить перенаправление и отсутствие циклов; исчезновение страницы без решения блокирует приёмку миграции.
- Проверить соответствие метаданных, дат, авторства и атрибуции; отдельными случаями покрыть старый Markdown, bundle и материал без явного автора.
- Проверить, что черновики, будущие материалы и служебные файлы не попадают в публичный вывод. Сверить основные HTML-метаданные, навигацию, sitemap, RSS и поиск. Учесть фактические правила выкладки и удаления файлов перед выпуском.
- Повторить затронутые сценарии редакции. Зафиксировать версии генераторов, команды, вход, ожидаемый и фактический результат. Новый профиль вступает в силу только после согласованной приёмки.

Для оценки Astro использовать [официальное руководство по миграции с Hugo](https://docs.astro.build/en/guides/migrate-to-astro/from-hugo/): Markdown и часть полей можно перенести, но шаблоны и Hugo shortcodes требуют отдельных решений. Поддержка Astro в ITDOXY не проверялась.

## Действующий профиль темы

Для пилота применяется закреплённый PaperMod в `themes/PaperMod/`. Профиль темы описывает вывод страницы, оформление и навигацию отдельно от версии Hugo и команд сборки. Смену темы можно выполнять без смены генератора. Если новой теме нужны другие поля, сопоставление согласовать отдельно; правила публикации сохраняются.

| Что фиксируем | Сейчас в ITDOXY |
|---|---|
| Тема и версия | PaperMod, submodule; зафиксировать commit темы и проверяемое состояние сайта |
| Переопределения | `layouts/single.html`, `layouts/basic_page.html`, `layouts/_partials/`; при замене темы проверить, какие файлы сохраняются и какие нужно адаптировать |
| Страница статьи | Заголовок, автор и даты, описание, обложка, оглавление и якоря; применимость полей проверять в собранном HTML |
| Навигация и чтение | Внутренние ссылки, категории, поиск, мобильный вид, доступность клавиатурой и читаемость кода и таблиц |
| Метаданные и вывод | Canonical, description, Open Graph и структурированные данные; проверить выход по профилю генератора, включая sitemap, RSS и индекс поиска |

В общих Skills проверяйте результат для читателя, а не классы CSS или структуру DOM конкретной темы. Селекторы и пути шаблонов, если они нужны автоматизации, относятся к профилю темы.

### Проверки при замене темы

Это отдельная проверка будущей замены, а не расширение матрицы `article-update`. При замене только темы сравнить старую и новую темы в изолированных сборках одного снимка контента с той же версией генератора. Предварительно описать намеренные визуальные изменения; совпадение внешнего вида по пикселям не требуется.

- Сверить набор опубликованных URL, canonical, используемые якоря, внутренние ссылки и ресурсы. Потеря страницы или ссылки без согласования блокирует приёмку.
- Проверить сохранение заголовков, авторства, дат, описаний, изображений и alt, Open Graph и структурированных данных. Сверить sitemap, RSS, поиск и навигацию, если вывод зависит от шаблонов.
- Проверить типовую статью и page bundle на узком и широком экране: меню, оглавление, переходы с клавиатуры, видимость фокуса и читаемость. Зафиксировать ожидаемые отличия и регрессии.
- Убедиться, что черновики и служебные материалы не появились в production. Если одновременно меняется генератор, дополнительно выполнить его миграционные проверки.
- Записать версии темы, настройки, снимки или фактические результаты, условия приёмки и отката. Профиль темы обновляется после согласованной приёмки, а не по факту скачивания новой темы.

### Проверка истории перед публичной отправкой

Проверка всех реально отправляемых коммитов обязательна до push, но не является условием запуска локального пилота без отправки. Для будущего инструмента проверки истории предусмотреть сценарий: синтетическое чувствительное значение добавлено и затем удалено, итоговый diff чист, но история обнаружена проверкой. Использовать подготовленную тестовую историю либо отдельный временный репозиторий; создание даже тестовых коммитов требует явного запроса пользователя. До разрешения никаких тестовых коммитов не создавать. Не объявлять непроверенный инструмент надёжным и не подменять проверку фактического диапазона фикстурой.

## Остальные режимы после пилота

- article-from-sources: переданные источники прочитаны; дополнительные отмечены; до утверждения плана нет статьи; затем только новый draft.
- article-from-topic: поиск и первичные доказательства до плана; недоступность не заменяется выдумкой; новый draft после утверждения.
- discover-topics: проверены пересечения, гипотезы отделены от измерений, только отчёт.
- content-audit: полный реестр, согласованный углублённый охват, служебные _index исключены из обычных статей, риск отделён от дефекта; статьи не меняются.
- При изменении общих Skills повторить затронутые U-сценарии.

Для видео добавить после основного пилота проверки SRT, VTT, кириллицы, многострочных реплик, тегов, повторов, повреждённого файла и неизменности входа. Проверить отдельно отсутствие транскрипции, ошибки ASR и недоступность экрана. Полноценная поддержка видео не заявляется до этого.

## Приёмка и журнал

В review перечислить ID, фактические доказательства и ограничения. Валидация OpenSpec после его настройки:

```bash
openspec validate add-article-update-pilot --strict
openspec validate --all --strict
```

Эти команды проверяют структуру, но не факты, загрузку Skills и прохождение U-сценариев. Не отмечать неисполненные проверки выполненными.

Принятие пилота требует выполненных обязательных проверок и отсутствия блокирующих дефектов. Если критическая проверка невозможна, результат «не принято» либо delta критериев на новое согласование. Архивирование — после явной приёмки, без Git-коммита. Полный MVP требует ещё четырёх принятых режимов; это не условие старта пилота.

Перед push/PR использовать охват [публичности](article-quality.md); перед выпуском — финальные base/head, совмещённое дерево и URL по [процессу](editorial-workflow.md). Полный CI и деплой в рамках локальных тестов не запускать.
