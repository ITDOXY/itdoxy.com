## Назначение и ответственность

AI-редакция помогает исследовать темы, готовить русскоязычные технические статьи, проверять и актуализировать архив. Codex готовит результат; редактор отвечает за выбор темы, согласование объёма, достоверность итогового материала и решение о выпуске.

Утверждение плана не разрешает публикацию. **Коммит делает пользователь самостоятельно либо Codex по явному запросу.** Подробнее: [процесс и полномочия](editorial-workflow.md).

## Быстрый старт после реализации

1. Откройте репозиторий сайта как основной локальный проект Codex Desktop. Для первого пилота используйте последовательные чаты в одном Local checkout.
2. Проверьте путь, ветку, рабочее дерево и действующие `AGENTS.md`. Не переключайте ветку и не сбрасывайте чужие изменения автоматически.
3. Используйте [действующий профиль генератора](editorial-testing.md#действующий-профиль-генератора). Для пилота это Hugo Extended версии CI `0.168.0`. Обычная локальная команда `hugo` на момент аудита использовала `0.169.0`; проверьте `hugo version`.
4. Для изменения системы используйте согласованную версию OpenSpec и профиль `core`. Порядок установки — в плане; для обычного редактирования статей установка OpenSpec не является самостоятельным этапом каждого задания.
5. Проверьте обнаружение нужного репозиторного Skill и чтение его `SKILL.md`. Если Skill не загружен, остановите сценарий и исправьте настройку.
6. Задайте тему, аудиторию, задачу читателя, исходники и границы. До согласования плана или объёма не переходите к изменению статьи.

Локальный Skill размещается в `.agents/skills/<name>/SKILL.md` с метаданными `name` и `description`. Обнаружение проверяется по [методике тестирования](editorial-testing.md), а не только по фразе агента «использую Skill». [Официальная документация Skills](https://learn.chatgpt.com/docs/build-skills)

## Режимы

| Skill | Когда использовать | Результат |
|---|---|---|
| article-from-sources | Есть тема и материалы | Research, утверждённый план, черновик |
| article-from-topic | Есть тема | Поиск источников, research, план, черновик |
| discover-topics | Нужно выбрать темы | Обоснованный отчёт без изменения статей |
| article-update | Нужно проверить конкретную статью | Досье, предложение, согласованный diff и ревью |
| content-audit | Нужна оценка архива | Реестр, охват проверки, очередь обновлений |
| research | Общая работа с источниками | Доказательства, противоречия и ограничения |
| article-review | Общая проверка результата | Замечания, результаты проверок и решение |

Примеры для новых чатов после создания и проверки Skills:

```text
Используй article-update для <путь>.
Сначала проверь исходную версию и research.
При отсутствии досье восстанови его с отметкой происхождения.
Покажи минимальный объём изменений и дождись утверждения.
Коммит, push и публикацию не выполняй.
```

```text
Используй article-from-sources.
Тема: <тема>. Аудитория: <уровень>. Источники: <ссылки>.
Сначала research и план. Статью до утверждения не пиши.
```

```text
Используй article-from-topic для <темы>.
Найди первичные источники, укажи версии и подготовь план.
```

```text
Используй discover-topics: предложи 10 тем после анализа архива.
Отдели измеренный спрос от гипотез. Статьи не создавай.
```

```text
Используй content-audit: составь реестр, согласуй глубину проверки,
укажи подтверждённые дефекты, признаки риска и непроверенные материалы.
Статьи не изменяй.
```

## Где хранится результат

| Каталог | Роль |
|---|---|
| docs/ | Руководство и редакционная методика |
| docs/plans/ | План внедрения и фактический прогресс |
| openspec/specs/ | Принятые требования к системе |
| openspec/changes/ | Будущие предложения изменений системы |
| .agents/skills/ | Skills OpenSpec и три проверенных редакционных Skills пилота |
| docs/editorial-templates/ | [Готовые шаблоны досье](editorial-templates/README.md) |
| research/ | Будущие публично подготовленные досье статей |
| reports/editorial/ | Отчёты проверок и приёмки пилота; будущие отчёты тем и аудита |
| scripts/editorial/ | Будущие проверочные инструменты |

Git игнорирует корневой каталог `work/editorial/`. Используйте его для неконфиденциальных временных материалов. Конфиденциальные данные храните вне репозитория. Временные материалы держите вне `content/` и `static/`.

## Если генератор или тема изменятся

Стиль, research, согласования и публичность сохраняются. Сборка, preview, пути, поля и правила вывода описаны в отдельном разделе [профиля генератора](editorial-testing.md#действующий-профиль-генератора). Возможный переход на Astro или Gatsby оформляется отдельным OpenSpec change с проверкой опубликованных URL, ресурсов и исключения черновиков. Сейчас описан только профиль Hugo; переход не входит в пилот.

[Профиль темы](editorial-testing.md#действующий-профиль-темы) фиксирует PaperMod, переопределения шаблонов и проверки результата для читателя. Тему можно заменить при сохранении Hugo; такая замена проходит отдельное согласование и сравнение страниц, навигации, доступности и SEO. Правила исследования и согласований сохраняются.

## Commit, публичная отправка и выпуск

Перед коммитом проверьте файлы, до публичного push — всю отправляемую историю, перед PR — актуальный head. Подробные критерии находятся в [article-quality.md](article-quality.md), порядок согласований — в [editorial-workflow.md](editorial-workflow.md).

`draft: true` не скрывает файл на GitHub. OpenSpec archive не является Git-коммитом и не разрешает публикацию. В ITDOXY решение о выпуске принимается человеком, а деплой после push в `main` выполняется автоматически. Ручной `workflow_dispatch` также публикует сайт. Проверять сборку таким запуском нельзя.

## Ограничения

Сборка не доказывает фактическую точность. Субтитры не доказывают содержимое экрана. Отсутствие тестовой среды не превращает критическую проверку в необязательную. Публичные файлы не должны содержать конфиденциальные сведения. Принятие этих документов не означает приёмку ещё не созданных Skills или спецификаций.
